# ADR-007. Проект вдвоём

Статус: принято. Дата: 2026-09-07.

## Контекст

Интерьер редко выбирает один человек. Спека описывает второго участника проекта: владелец зовёт его письмом, тот входит по ссылке, оба отмечают концепты и видят отметки друг друга в реальном времени, вкладка «Общие» показывает совпадения, а если совпадений нет, сервис предлагает три компромиссных варианта. Второй участник не платит, не удаляет проект и не приглашает других.

## Решение

**Роль живёт рядом с проектом, а не в таблице пользователей.** `project_collaborators` хранит второго участника с ролью `partner`; владелец остаётся в `projects.owner_id` и не дублируется, частичный уникальный индекс держит одного участника на проект. Проверка доступа возвращает роль, и всё, что меняет проект или стоит денег, требует владельца: настройки, комнаты, файлы, генерация, перекраска, список покупок, экспорт, оплата. Чужой проект по-прежнему неотличим от несуществующего, а закрытый владельцем проект второй участник видит как честную страницу «Владелец закрыл проект», потому что удаление мягкое.

**Приглашение — отдельная таблица с хэшем токена.** Приглашение появляется раньше аккаунта адресата, поэтому в `project_invites` лежит почта, а не `user_id`. В базе хранится только SHA-256 токена; сам токен уходит в письмо и живёт неделю, новое приглашение заменяет висящее. Принять его может только сессия с тем же адресом.

**Вход по ссылке — плагин magic-link Better Auth, но только для новых адресов.** Для существующего аккаунта с неподтверждённой почтой вход по ссылке в Better Auth удаляет пароль и сессии как «недоказанные», поэтому людям с аккаунтом уходит обычная ссылка на страницу приглашения, а magic-link получают только те, у кого аккаунта нет. Публичный эндпоинт плагина остаётся, но письмо отправляется лишь под живое приглашение на этот адрес; хэш токена в базе, срок сутки. Аккаунт из ссылки живёт без пароля: страница приглашения сразу предлагает его задать через серверный `setPassword`, а «Забыли пароль?» создаёт пароль и позже.

**Приглашения доступны в оплаченном проекте и в Pro**, как коллаборация в тарифах спеки.

**Живой канал свой, на Redis и SSE.** В Trigger.dev v4 realtime привязан к запускам задач, отдельных каналов нет, а держать долгий запуск на каждую комнату дорого и хрупко. Поэтому страница держит соединение `GET /api/projects/[id]/live`: сервер раз в две секунды одной командой читает версию проекта и ключ присутствия второго участника, при изменении версии перечитывает отметки комнаты из базы и шлёт их целиком. Само соединение и есть присутствие: ключ с TTL 45 секунд обновляется, пока страница открыта, и снимается при закрытии, время ухода запоминается. Любая отметка поднимает версию проекта одним `INCR`. Задержка до двух секунд, внешних сервисов нет.

**Отметки в двух колонках, интерфейс считает срезы сам.** `liked_by_owner` и `liked_by_partner` заполняются по роли того, кто голосует; страница комнаты получает все концепты комнаты и делит их на «Мои», «Имя» и «Общие» чистыми функциями, локальный голос ложится поверх серверных, чужие приходят по каналу. Карточка в стопке носит метку, если второй уже отметил её, строка «только что» показывает последнюю чужую отметку.

**Варианты на двоих — Haiku 4.5 через fal плюс обычная генерация.** Когда оба оценили не меньше десяти готовых концептов комнаты и ни один не понравился обоим, модель получает лайки и дизлайки каждого и возвращает три варианта: название, идея по-русски и правка по-английски. Ответ кэшируется в Redis по хэшу отметок, поэтому оба видят одно и то же; запускает рендеры только владелец. Задача `generate-concept` принимает эти три правки как вариации поверх шаблонной общей части промпта, помечает запуск `batch_kind = duo`, кладёт название в `title`, а идею — в подпись концепта.

## Последствия

- Себестоимость: предложение около $0.003, три рендера около $0.25 по кнопке владельца; живой канал бесплатен, но держит по одному запросу к Redis в две секунды на открытую страницу комнаты.
- Письма: приглашение, «участник принял приглашение» владельцу; уведомлений о каждой отметке нет, для этого есть живой канал.
- E2E проверяет весь путь на двух контекстах браузера с концептами, посаженными в базу; предложение вариантов на двоих в CI показывает объяснение без ключа модели.
- Второй участник в проекте один; несколько участников и права на правки потребуют отдельного решения.
