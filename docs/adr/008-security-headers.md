# ADR-008. Политика безопасности контента и доверие обратному прокси

Статус: принято. Дата: 2026-09-07.

## Контекст

С Фазы 1 в чек-листе висели два долга. Первый: приложение отдавало только базовые заголовки, политики безопасности контента не было вовсе, поэтому любой скрипт, попавший в разметку через чужие данные, браузер бы выполнил. Второй: адрес клиента брался из первой записи `X-Forwarded-For`, а её присылает сам клиент — лимиты по IP обходились одним заголовком, а в журнал аудита попадал выдуманный адрес.

## Решение

**Политика собирается на каждый запрос и несёт одноразовый номер.** Прокси Next.js кладёт `Content-Security-Policy` и в запрос, и в ответ: из запроса Next.js достаёт номер и проставляет его своим тегам `script`, из ответа политику читает браузер. Номер — шестнадцать случайных байт в base64, свой для каждого ответа, поэтому заранее подобрать его нельзя.

**`strict-dynamic` вместо перечня доменов.** Скрипты выполняются, только если у них есть номер, плюс всё, что такие скрипты загрузили сами, — это ровно модель Next.js: несколько тегов с номером тянут остальные чанки. `'self'` оставлен рядом ради браузеров, которые `strict-dynamic` не понимают. Перечислять домены не нужно: своих внешних скриптов у нас нет.

**Инлайновые стили разрешены осознанно.** `next/font` подставляет теги `style`, а анимация свайпа пишет трансформации в атрибут `style`; привязать к ним номер нельзя, поэтому `style-src` разрешает инлайн. Для защиты от подмены скриптов это ничего не меняет.

**Картинки и подключения оставлены широкими.** Товары приходят с доменов магазинов, очередь задач и сбор ошибок живут на своих адресах — перечислить это в политике нельзя без постоянных правок. Поэтому `img-src` и `connect-src` разрешают `https:` целиком плюс адрес хранилища файлов из `S3_ENDPOINT`: локально оно работает по http, и без явного разрешения подписанные ссылки на планы и рендеры не открывались бы.

**Поднятие протокола включается по адресу приложения, а не по `NODE_ENV`.** `upgrade-insecure-requests` добавляется, только когда `APP_URL` начинается с `https://`. Иначе продовая сборка, запущенная локально по http, переписывала бы ссылки на MinIO в https и роняла все картинки — на этом и попался первый вариант политики.

**Адрес клиента разбирается один раз, в прокси.** Настоящий адрес дописывает в конец `X-Forwarded-For` наш обратный прокси, всё, что стоит перед ним, прислал клиент. Поэтому запись берётся с конца, отсчитывая по числу своих прокси из `TRUSTED_PROXY_HOPS` (за Coolify — один). Результат кладётся в заголовок `X-Client-IP`, который прокси всегда перезаписывает, поэтому подсунуть его снаружи нельзя. Лимитер, аудит и Better Auth читают только его и сырых заголовков больше не видят.

**Вебхук ЮKassa сверяет тот же разобранный адрес.** Раньше маршрут уведомлений брал первую запись `X-Forwarded-For` и на ней проверял принадлежность подсетям ЮKassa: любой отправитель мог подставить чужой адрес и пройти проверку. Теперь маршрут читает тот же `X-Client-IP`, а особый случай `CF-Connecting-IP` убран — если перед приложением появится Cloudflare, это лишний прокси в счётчике, а не отдельный заголовок.

**Ноль прокси означает «не верим никому».** Если приложение смотрит в сеть напрямую, `X-Forwarded-For` подделывается кем угодно, поэтому при `TRUSTED_PROXY_HOPS=0` заголовок игнорируется целиком: запросы считаются одной корзиной, а в аудит адрес не пишется. Это честнее, чем записывать заведомо ложный адрес.

## Последствия

- Все ответы приложения проходят через прокси Next.js, включая маршруты API и вебхук ЮKassa; статика из `_next/static` исключена матчером и политики не несёт, документами она и не является.
- Проверка в браузере по основным экранам — проекты, комната, концепт с канвой перекраски, итоги, профиль — даёт ноль нарушений политики, все 23 тега `script` получают номер.
- При переезде за дополнительный прокси, например Cloudflare перед Coolify, нужно поднять `TRUSTED_PROXY_HOPS` до двух, иначе в аудит попадёт адрес пограничного узла Cloudflare, а не клиента.
- Широкие `img-src` и `connect-src` — сознательный компромисс: они не мешают краже данных через `https:`-адрес, но основную дыру, выполнение чужого скрипта, закрывает `script-src`. Сузить их можно, когда список доменов магазинов стабилизируется.
