# Проверка пожеланий после рендера

## Изменения

- Проверяющий получает notes, revision и household из существующего брифа.
- brief_conflict обозначает видимое противоречие; requirement_unconfirmed — пожелание,
  которое кадр не подтверждает. Не запускаем автоматический повтор рендера.
- Размеры передаются без округления до десятых метра. Освещение не требует новых окон.
- Карточка сохраняет оговорки о размерах и неполной проверке; после перекраски старый отчёт скрыт.

## Проверки

388 модульных тестов, включая парсер новых кодов, передачу/ограничение заметок,
невалидные ответы, таймаут без повторного запроса, текст и экранирование карточки.
Проверка типов во всех пакетах и lint выполняются отдельно перед выпуском.

Повторная оценка шести локальных синтетических изображений без новых рендеров:

| Пример | Результат |
| --- | --- |
| narrow-kitchen | unavailable, результат не объявлен проверенным |
| small-family-kitchen | requirement_unconfirmed: три места запрошены, два видны |
| narrow-living | checked, замечаний нет |
| two-window-living | checked, замечаний нет |
| compact-bedroom | checked, замечаний нет |
| windowless-bedroom | checked, замечаний нет |

Два дополнительных запроса на том же изображении two-window-living:
- условие «никаких кресел» → brief_conflict, кресло справа;
- архитектура «нет окон» → opening_conflict, видны два окна.

Всего восемь обращений к проверяющему, ноль новых рендеров.
Не считать контрольные запросы самостоятельными генерациями или оценкой общей точности.

### Повторная оценка с полным брифом

Контрольный прогон теперь передаёт проверяющему не только тип комнаты и архитектуру, но и
пожелания, позднюю правку и состав семьи. Старый результат без этих данных не считается
актуальным; сохранённые изображения используются повторно, поэтому новые рендеры не создаются.

Первый прогон новой версии:

| Пример | Результат |
| --- | --- |
| narrow-kitchen | checked: линейная кухня, окно и складной стол видны |
| small-family-kitchen | requirement_unconfirmed: видно два места вместо трёх |
| narrow-living | opening_conflict: дверь оказалась на длинной боковой стене |
| two-window-living | unavailable |
| compact-bedroom | unavailable |
| windowless-bedroom | unavailable |

Доступные проверки с намеренно неверным типом комнаты во всех трёх случаях заметили
`wrong_room`. Недоступный ответ не кешируется как успешный и будет переоценён в следующем
прогоне. В этом проходе было двенадцать обращений к проверяющему и ноль новых рендеров.

Во втором проходе `narrow-living` сменился с `opening_conflict` на `checked`, а
`windowless-bedroom` стал доступен и получил `checked`; `two-window-living` и
`compact-bedroom` остались `unavailable`. Это показывает вероятностность визуальной проверки:
её замечания остаются подсказками человеку, не запускают скрытую перегенерацию и не объявляют
геометрию доказанной. Для экономии повторяется только недоступная основная проверка; сбой
калибровочного запроса с неверным типом комнаты не заставляет повторно проверять готовый результат.

На третьем проходе `two-window-living` восстановился и получил `checked`; только
`compact-bedroom` снова остался `unavailable`. После этого автоматические повторы остановлены:
неограниченно тратить запросы ради вспомогательной проверки нельзя.

### Типовые российские кухни

В выборку добавлены ещё три синтетических брифа без пользовательских данных:

- кухня 2,15 × 2,40 м для семьи из трёх человек, с радиатором под окном;
- кухня 3,00 × 3,40 м с отдельными окном и балконной дверью;
- вытянутая кухня 2,50 × 3,90 м с двумя входами и сквозным проходом.

Генератор теперь получает отдельное требование сначала составить внутренний перечень всех
окон, дверей, входов и балконных проёмов, сохранить их количество и не сливать соседние
проёмы в панорамное остекление. QA-скрипт умеет запускать один выбранный пример через
`QUALITY_BENCH_CASE`, чтобы диагностическая проверка не запускала всю платную выборку.

Живой прогон новых примеров не состоялся: fal.ai вернул `403` с причиной `Exhausted balance`.
Ни один новый рендер не был получен. Автоматические повторы остановлены до пополнения баланса;
готовность промптов подтверждена модульными тестами, но визуальный результат пока не подтверждён.

После пополнения баланс отобразился в кабинете, но API продолжил частично отвечать `403` с
причинами `TOP_UP` и `Exhausted balance`: fal предупреждает, что обновление может запаздывать.
Один запрос `khrushchev-family-kitchen` прошёл. На нём сохранились одно окно, радиатор под ним,
вход справа и три посадочных места, однако комната визуально вытянулась, а на кухне появились
диван и детские книги. Причина лишней мебели найдена в общей логике семьи: детский уголок,
рабочее место и место питомца раньше добавлялись почти в каждую комнату. Теперь детский уголок
ограничен гостиной и детской, рабочее место — гостиной и спальней, место питомца — жилыми
комнатами; кухня получает только число мест и потребность в рабочей поверхности.

Принудительный холст `16:9` также убран. Для почти квадратных комнат без фотографии теперь
используется `4:3`, для умеренно вытянутых — `3:2`, для длинных — `16:9`; при редактировании
фотографии передаётся `auto`, чтобы сохранить исходный формат. Все эти значения поддерживаются
API Nano Banana 2. Визуально подтвердить исправление можно после окончательной разблокировки API.

Повторная одиночная попытка после пополнения снова получила `403 Exhausted balance`, хотя в
веб-кабинете уже отображалось $9,67. Вероятные причины — задержка синхронизации пополнения либо
ключ из другого рабочего пространства. До сверки ключа и снятия блокировки новые запросы
остановлены.
Локальные изображения и сырые ответы исключены из Git.

## QA Release Gate

BLOCKERS для точного проекта по размерам остаются: нет геометрической валидации,
сравнения с исходным планом/фото и гарантированного сохранения архитектуры между вариантами.

IMPORTANT: малая нерепрезентативная выборка; один unavailable; возможны ложные
предупреждения и пропуски. Требуется дальнейшая размеченная выборка.

POLISH: отсутствие предупреждений не означает исполнения всех пожеланий; это явно сказано в UI.

Рекомендация: выпускать как рекомендательное улучшение концептов, не как точную планировку.
Схема JSONB аддитивная, SQL-миграция не нужна; старые отчёты остаются совместимыми.
Старые пользовательские концепты не перезаписывались и не перепроверялись на сайте.
