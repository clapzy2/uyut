# Внешние полные копии и защита входа

Проверка 5 октября 2026; продолжение пакетов 5–6. Основная квартира владельца,
исходные планы, покупки и цены не менялись. Новые тарифы/подписки и генерации
не оформлялись. Использовано уже настроенное резервное хранилище.

## Выявленная публичная политика — исправлена

Проверка существующего объекта, а не пустого URL, выявила публичный GetObject
в резервном бакете: прямое чтение файла и SQL-архива возвращало HTTP 200 без
авторизации. ACL объектов и бакета сами по себе были private; доступ открывала
отдельная политика Allow для AWS `*`, только GetObject на объекты этого бакета.
В Coolify к данному резерву привязана только база приложения Домица.

Полная загрузка останавливалась на первом файле и не публиковала manifest.
Два собственных неполных дубликата удалены после сверки точных ключей и SHA-256;
исходники и локальная полная копия сохранены. Никакие SQL-архивы не удалялись.
Сохранена прежняя политика приватно, убран только этот публичный read-grant.
После изменения: анонимное чтение SQL-архива отклонено HTTP 403, чтение с ключом
работает, размер и ETag архива совпали. Основной бакет отдельно проверен:
анонимный доступ 403, публичной политики нет; его настройки не менялись.

Это факт прежней доступности, не доказательство чужого скачивания. Не утверждаем,
что архивы никто не читал. Владельцу объяснён риск; он явно согласовал завершение
прежних сеансов после публикации. Политика удалена по точному назначению, не
переключением всех бакетов аккаунта. Реквизиты и пути объектов в GitHub не включены.
Поведение политик проверено по [документации провайдера](https://timeweb.cloud/docs/s3-storage/manage-storage/manage-buckets/bucket-policies).

## Безопасная внешняя цепочка

Добавлены внешний upload/download полного снимка, строгий envelope, связь
с SHA-256 конкретного внешнего архива PostgreSQL и очистка поколений по сроку.
Новый снимок получает уникальный UUID и IfNoneMatch; файлы перечитываются
и проверяются по байтам, SHA-256, Content-Type и приватности. Manifest пишется
последним. Его отсутствие не выдаётся за завершённую копию.

Отказ до первой пользовательской записи проверяется созданным несекретным
nonce-probe: explicit ACL private, read-back и анонимный 403, затем удаление
именно своего probe. Отсутствующий URL с 403 не считается доказательством
приватности. Ошибка probe не допускает загрузку пользовательских данных.
37 целевых external-тестов, в том числе absent403/created200, прошли.

Источнику доступны только List/Get. Резервный бакет отличен от источника даже
при разных endpoint-алиасах. Download требует новый каталог, полный checksum
контроль и manifest последним. Секреты идут только через память/stdin, не argv,
репозиторий или журнал. Ключи берутся из актуальной конфигурации Coolify при запуске.

Владелец поручил выбрать срок. Принято: ежедневные 30 дней, копии за первое число
месяца по Москве — 12 месяцев. Самый новый завершённый снимок всегда сохраняется.
Очистка начинается только после новой проверенной загрузки: сначала удаляется
указатель старого поколения, затем только указанные в нём собственные файлы.
Другие источники, незавершённые префиксы, исходный бакет и архивы БД не удаляются.
Локальный настоящий Minio-прогон подтвердил upload → download → restore, удаление
старого поколения, сохранение месячного/нового и неизменность исходника/архива БД.
Это synthetic-контроль заголовка PGDMP, не повтор принятого pg_restore.

## Настоящий серверный таймер и восстановление

Служба `domitsa-file-backup.service` использует имеющийся web-образ Node и
скомпилированный runner; отдельный контейнер без публичных портов, read-only FS,
ограничения памяти/CPU и временное хранилище. `flock` и systemd запрещают наложение.
Расписание `domitsa-file-backup.timer`: ежедневно 07:00 Europe/Moscow, после
успешной копии базы примерно в 06:00. Ошибка даёт ненулевой exit, не фиктивный success.

| Первичная внешняя проверка | `3532b7d3-7acc-41a2-a513-12116fd54288` | 376 файлов, 34 660 213 байт |
| Та же служба на сервере | `f1566bdc-e593-49ca-9d7f-0b53c825b828` | success, те же 376 файлов |
| Реальный запуск таймером, 10:57 Москвы | `fbe43a84-0e91-4d19-8c2a-e0c09c068668` | success; служба 07:57:00–07:58:11 UTC |

Для принятия таймера временно поставлен однократный контрольный календарь;
после запуска override удалён, ежедневный календарь восстановлен. Следующий
запуск — 6 октября 07:00 Москвы, timer active/enabled. Этот будущий запуск
ещё не наблюдался; первый настоящий timer-run уже наблюдался.

У всех трёх снимков проверен архив базы от 5 октября 06:00:06 Москвы:
SHA-256 `7b69855c31e9083759c2283e4c4d983e58258b5b8e5174e9ff34ef223130561b`.
Проверяются размер, PGDMP, текущая ревизия/ETag до и после чтения, возраст <=26 ч.
Это связь с реальным архивом, но не атомарный снимок БД и объектов.

Именно timer-generation скачан из внешнего резерва: все 376 файлов проверены,
затем восстановлены под исходными ключами в новом изолированном Minio. Байты,
SHA-256, размеры и Content-Type совпали, анонимный доступ отклонён; исходник
подключался read-only. SHA-256 manifest восстановленной копии:
`83256316654d4b944ada779dae905321d8b7c2e3dc42d7bbae74849331dde2fc`.
Свои контейнер/сеть убраны; источник, исходные архивы и копии сохранены.

Два бакета находятся у одного провайдера/аккаунта: это защита от потери сервера
и обычной ошибочной записи, не независимый домен отказа/компрометации провайдера.
Срок файловых поколений не меняет прежнее хранение SQL в Coolify. Не выдаём
старый SQL-архив вне периода файлов за полное восстановление квартиры.

## Две ошибки пользовательского пути

Отказ или потеря сети при «Нравится» больше не оставляет ложный сохранённый
выбор: состояние возвращается, сообщение видно, быстрый второй клик блокируется.
Refresh вызывается только после успеха. Первый шаг после истечения входа
сохраняет project в next вместо создания другой квартиры. 45 целевых
проверок этих интерфейсных веток прошли; физический телефон этим не принят.

## Отзыв входов — согласован, до публикации не выполнен

Браузерный session_data cache отключается; Redis и React.cache остаются.
Простое удаление SQL не отзывает 15-минутную браузерную копию. Также реальный
SDK в in-memory контроле показал гонку refresh: он способен заново записать
Redis-токен после удаления SQL. Поэтому операция проводится только после
короткого stop/drain именно контейнера Домицы; companion с тем же SDK отзывает
сеансы в БД/Redis, проверяет ноль, затем сайт возвращается в finally.
Rate-limit пространство и пароли/аккаунты не очищаются.

Отдельная новая PostgreSQL/локальный Redis приняли настоящий compiled CLI:
два сеанса, включая токен с потерянным active-sessions индексом, отозваны;
пароль/аккаунт и контрольный rate-counter неизменны; свежий сеанс создаётся.
Тестовая БД удалена. Перед фактическим отзывом проверяется точная опубликованная
версия единственного web-контейнера. Не запускаем это как публичный endpoint.

Текущая проверка типов/lint успешна; локальный unit-набор 2617 прошёл.
Публикация общей пачки и живой отзыв/повторный вход остаются последним шагом.
