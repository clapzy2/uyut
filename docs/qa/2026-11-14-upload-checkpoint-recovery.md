# PDF загружен, но ответ о сохранении потерян

## Изменение

Раньше после успешной загрузки PDF отказ записи ready оставлял файл без доступного
результата. Повтор мог снова вызвать подготовку документа. Теперь до загрузки
воркер сохраняет контрольную запись: ключ с SHA-256 именно байтов PDF, число
страниц и подготовленное ТЗ. Для оплаченного PDF ТЗ по-прежнему обязательно.
Ключ имеет вид projects/<project>/exports/<export>-<sha256>.pdf.

В S3 передаются export-id и pdf-sha256. При потере ответа загрузки или финальной
записи заявка остаётся running, а не разрешает новую сборку. Повтор обработчика
подготовленного exportId не вызывает модель/печать/загрузку.

При чтении страницы и недоступной либо завершённой очереди сервис проверяет
HEAD объекта. Только совпадение пути, идентификатора, отпечатка, PDF MIME и
ненулевого размера позволяет подтвердить ready. Обновление БД связано с тем же
ключом и активным статусом. При смене контрольной записи чужой результат не
подтверждается. 403/timeout/несовпадение оставляют заявку для проверки. 404
разрешает отказ только после конечного статуса очереди. Пока задача выполняется,
дополнительных запросов S3 нет.

При восстановлении durationMs остаётся null: полное время после обрыва неизвестно.
finishedAt означает время подтверждения результата. Миграции БД не нужны.

## Проверено локально

- 9460 unit passed; build/typecheck/Biome прошли.
- 14 интеграционных тестов: реальные БД и локальный S3, восстановление файла,
  неизвестный доступ, отсутствие, активная очередь, смена ключа во время HEAD.
- 2 E2E прошли. В существующий сценарий восстановления добавлено: запись running
  с контрольными данными + настоящая загрузка через helper воркера в локальный S3
  -> reload страницы -> ссылка того же PDF и ready в БД. Новых экспортов нет
  (2 записи до и после), модель/очередь не вызывались. QA-объект удалён после теста.
- Worker-тесты проверяют порядок записи и загрузки, потерянный ответ БД, отказ
  контрольной записи, ограничение времени передачи и отсутствие повторной подготовки.

## Границы

Это восстановление новых файлов с контрольной записью. Старые заявки без runId,
метки или такой записи автоматически не исправляются. Длительный отказ S3/БД
остаётся явной необходимостью повторить проверку, а не основанием платного повтора.
Одновременные ручные запуски одного exportId напрямую из панели очереди полностью
не сериализованы. Отправка письма после восстановления не добавлена: файл доступен
в проекте. Время сборки и недостающие данные не выдумываются.

Платных запросов не было, расход $0. Общие проценты готовности не повышаем.
