# Добавленная техника в автосверке

База: main `f58fc92`. Проверка использует сохранённый синтетический исходник
`output/layout-guide-production-20261106/render.png` и пять вариантов из
`output/live-photo-20261106/concept-{1..5}.webp`. Новые интерьеры не генерировались.
Живые проекты и сохранённые отчёты концептов не перезаписывались.

## Воспроизведение и правка

На прежнем коде повторная проверка варианта4 снова вернула checked, хотя под
окном появился радиатор. В исходнике этот участок стены открыт и пуст.
Источник и результат передавались правильно; ошибка была в сравнении:
инструкция явно перечисляла исчезнувшую/перемещённую технику, но не добавленную.

Теперь сравниваются оба направления. Перед выводом модель отдельно описывает
видимую область исходника в служебном sourceView; это поле не сохраняется в
проекте и не считается доказательством. Инструкция требует сопоставимого
открытого участка обоих кадров, но модель соблюдает это не всегда: отрицательный
контроль сильно обрезанного источника НЕ ПРОЙДЕН. Это частичное улучшение,
не надёжная проверка фотографий с произвольным различием охвата.

Режим выбирается кодом: finished/keep сохраняют стационарную технику, bare
допускает новое оснащение, неизвестный режим не превращается в запрет.
Явные пожелания и видимые конфликты остаются проверяемыми во всех режимах.
Проверяющий получает просьбу конкретного выбранного duo-варианта отдельно от
общих заметок. Приоритет: revision > requestedVariant > notes. Автоматические
стилевые предложения разрешением не становятся. Контекст сохраняется в
первой проверке якоря и в проверке корректирующего рендера.

## Сохранённые кадры и контроли

Модель та же: `anthropic/claude-sonnet-4.5`, тот же fal vision endpoint.
Один запрос на проверку; новых автоматических повторов или рендеров нет.

| Сценарий | Результат после исправления |
| --- | --- |
| Вариант2, лишний кондиционер | review, указано место над ТВ-тумбой |
| Вариант4, лишний радиатор | review, указана пустая стена под окном в исходнике |
| Варианты1/3/5 | Добавленная техника не заявлена; отдельное замечание к цвету тумбы в №1 описано ниже |
| Радиатор явно разрешён поздней просьбой | checked |
| Кондиционер явно разрешён поздней просьбой | checked |
| Радиатор разрешён выбранным duo-вариантом | checked |
| Поздняя просьба отменяет добавление радиатора | review |
| Радиатор присутствует в обоих одинаковых кадрах | checked |
| Нет исходного кадра | checked, сравнение до/после не выдумано |
| Исходник обрезан до левой части, стена под окном не видна | Нестабильно: отдельные checked, в повторном контроле ложный review. FAIL |
| Режим bare с проектируемым отоплением | checked |
| Без фото: выбранный вариант разрешает радиатор вопреки старой заметке | checked после уточнения приоритета |

Обрезка - технический отрицательный контроль: x0..440 из исходника1200×896,
без генеративного дорисовывания. Bare использует тот же отделанный тестовый
кадр и проверяет соблюдение режима, а не реальный ремонт черновой квартиры.

В промежуточной версии были ложные замечания к обрезке и bare. Они сохранены
в `final/` и `refined/`, не удалены. Разделение режима убрало конфликт
инструкций. Отдельное описание исходника помогло в `grounded/` и `acceptance/`,
но в `release-control/` ложное замечание к обрезке повторилось. Диагностика
показала противоречие внутри ответа: sourceView правильно описывает окно
за кадром, а issues объявляет радиатор добавленным. Эксперимент с дополнительными
полями evidence в `evidence/` не помог; он удалён из кода. Parser, формат
сохранённых замечаний и число запросов в рабочем сценарии остались прежними.
Не добавляли ложные гарантии из наблюдений той же модели и не выдавали
непройденный контроль за успешный. Для отличающегося охвата нужна ручная
сверка; предупреждение модели не является доказанным изменением квартиры.
Приоритет выбранной просьбы над старой заметкой без фото первоначально
применялся неверно; последняя правка проверена в `priority/`, включая обратный
случай, когда позднее уточнение снова запрещает радиатор.

В одном раннем вызове variant1 был unavailable, а не ложный checked. Повторная
диагностическая проверка выполнена отдельно, автоматических повторов нет.
В acceptance вариант1 получил замечание о смене цвета тумбы: фраза исходного
брифа «сохранить три основных предмета» неоднозначна на фоне просьбы обновить
мебель светлым дубом. Это не добавленная техника. Первоначальный regex ошибочно
считал упоминание «тумба под телевизор» замечанием о технике. Поэтому варианты
1/3/5 требуют визуальной оценки в benchmark (passed=null), а не автоматически
объявляются чистыми по поиску слов. Полные ответы сохранены. Эту неоднозначность
пожеланий не маскировали изменением исходных заметок.

Артефакты: `output/equipment-review-20261106/`. JSON содержит сценарий, бриф,
хеши отправленных кадров и полный итоговый отчёт. Это ограниченный проверочный
набор, не процент качества на произвольных фотографиях и не гарантия размеров.

Воспроизведение из корня (платные проверки, только при намеренном запуске):

```powershell
$env:EQUIPMENT_REVIEW_OUTPUT = 'output/equipment-review-next'
$env:EQUIPMENT_REVIEW_CASES = 'added-radiator,source-area-not-visible,bare-equipment'
bun --env-file=.env jobs/scripts/bench-equipment-review.ts
```

Без EQUIPMENT_REVIEW_CASES запускаются14 сценариев. Скрипт не перезаписывает
результат и отказывается повторно тратить запрос на существующий файл.
Имена файлов и синтетические изображения остались локально, в git не включены.

## Программные проверки

Добавлены7 регрессий: три режима запроса и четыре проверки настоящего тела job
с подменой внешних границ. Проверены порядок кадров, единственный POST,
раздельные поля/лимиты, разные duo-просьбы, сценарий без фото, первая проверка
якоря, корректирующая проверка и отсутствие разрешений из стилевых предложений.
Локально9149 тестов в362 файлах, итоговые34 профильных теста, типизация7
пакетов, форматирование и production build прошли. CI фиксируется после
завершения пакета. Старые qualityReview не пересчитываются автоматически:
выпуск изменяет новые проверки, а не исторические записи задним числом.
